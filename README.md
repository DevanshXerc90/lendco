# LendCo

LendCo is a small borrower-support agent that combines account context, policy
retrieval, payment diagnostics, actions, and call memory. It is designed to be
easy to run locally and easy to explain: the default planner is deterministic,
the data is synthetic, and every reported metric is generated by the evaluator.

```text
Borrower -> CLI/API -> Orchestrator
                         |-- context + memory
                         |-- diagnosis -> tools
                         |-- TF-IDF policy retrieval
                         `-- grounded reply + recorded action
                         `-> mock CRM / payments / support / workflow
```

## Demo

```text
AGENT  > Hello Aryan, how can I help you with your loan today?
BORROWER> My payment failed even though I had enough balance.
AGENT  > The latest failure appears to be bank-side, not caused by insufficient
          funds. I have created a retry payment link and cited the payment policy.
   [diagnosis] intent=payment_failure  tools=[get_gateway_logs,search_knowledge_base,create_payment_link]
```

Run the complete flow, including a readable transcript:

```powershell
python -m scripts.run_all
```

## Quickstart

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m scripts.run_all
```

Individual scenarios are available with `python -m app.cli --scenario waiver`,
`remaining`, `settlement`, `account`, or `ptp_memory`.

| Held-out intent accuracy | 98.3% (59/60) |
| Policy grounding rate | 100.0% (64/64) |
| Resolved without escalation | 87.5% (56/64) |

| Naive baseline turns / call | 2.62 |

The optional hosted planner is reported only when explicitly enabled with
`LENDCO_LLM=1` and `ANTHROPIC_API_KEY`; otherwise its result is `not_run`.
Known adversarial failures remain listed in
[`eval/results_adversarial.json`](eval/results_adversarial.json).

## Design properties

The planner never asks for slots that the account systems can derive. Repeat
calls use stored commitments and preferences before asking new questions.

## Security and deployment

Local mode uses mock services and local JSON/SQLite state. Production requires
`API_SECRET`, `DEMO_API_KEY`, and exact `CORS_ORIGINS`; protected API routes
require `X-API-Key`. Replace mock clients with authenticated service clients
before deployment.

## Limitations

The platform services and borrower records are synthetic local mocks.
There is no real identity verification or production PII control.
The retrieval index is local TF-IDF rather than a hosted vector store.
